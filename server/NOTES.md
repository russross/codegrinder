Server semantics
================

This document defines the operation boundaries and invariants to preserve when changing the Rust TA and daycare server. The wire contract is [codegrinder.proto](../protocol/codegrinder.proto); database policy is defined in [schema.sql](../setup/schema.sql). Client obligations are documented for [grind](../grind/NOTES.md), [web](../www/web/NOTES.md), and [VM client](../www/vm/NOTES.md). Protocol changes require explicit approval.


Identity, state, and authority
------------------------------

An assignment is identified by `(user_id, course_id, problem_set_id)`. A saved problem step adds `(problem_id, step_number)`. There is one current commit per assignment problem step; saves replace its complete file set rather than append an immutable history. Creation time is retained on update; persistence timestamps come from the server.

Problem sets define the scope of scoring and progression. A set contains complete problems with weights, or an inclusive step slice of exactly one problem. A slice beginning after step one must continue a slice of the same problem ending immediately before it. Commits remain under their original assignment keys; continuation never migrates them.

The TA owns identity, authorization, canonical files, ownership, sequencing, persistence, and LMS bookkeeping. The daycare executes signed requests without querying assignment state. Clients transport signed bundles between the two. Browser execution and client-reported scores are never grading authority.

File maps contain normalized relative paths and byte contents. Reject invalid paths and normalization collisions before persistence or packaging. Submitted student paths must belong to the step's solution whitelist. System files and arbitrary extra files cannot become student-owned through a save. Contents are opaque bytes; author whitespace is not normalized.


Startup and request transactions
--------------------------------

1. Load configuration and open the existing SQLite database. Run full `ANALYZE` with no analysis limit on every startup, refreshing persisted planner statistics including STAT4 before accepting requests; failure aborts startup. Always enable TA bookkeeping and one local daycare in the same process. There are no role flags; configuration requires the LMS/session/signing secrets, positive capacity, and a nonempty supported problem-type list. `hostname` is the public execution host; there is no `taHostname` field. The production database/schema must already be provisioned.
2. Bind cleartext HTTP/h2c on `localhost:1400` by default. Caddy terminates public TLS, serves static assets, and supplies trusted forwarding information. Public HTTPS and certificates do not belong to the Rust process.
3. Serve LTI, version routes, administrative RPCs, and the existing daycare RPC on the same listener. TA requests perform authentication and short database work; daycare requests can run for the duration of student execution without occupying a TA transaction.
4. Delete expired sessions and schedule recovery of eligible pending/failed LMS passbacks on startup. Recovery must not block normal request handling on external services. There is no daycare registration task or registration HTTP endpoint.

Each database job opens its own connection on a blocking worker. Reads use `BEGIN`; potential writers use `BEGIN IMMEDIATE` before reading their mutation snapshot. A successful operation commits, and an error rolls back. Foreign keys, WAL, and full synchronous writes are enabled. gRPC deadlines cover connection setup, lock waits, SQL progress, and awaiting the worker.

Authentication can have a separate transaction from the requested operation. A multi-RPC workflow is not one transaction: a pre-execution save can succeed even if daycare or final persistence later fails. No transaction may span Docker execution, an LMS HTTP request, a client round trip, or a retry delay. A lost response is not proof that its transaction did not commit.


LMS launch and session establishment
------------------------------------

1. Parse the launch UI and problem-set identifier, reconstruct the public launch URL using proxy headers, and verify the LTI OAuth signature. Restricted launches additionally enforce approved IP ranges, with the instructor launch exception.
2. In one write transaction, resolve the problem set and upsert the course, user, course roles, and assignment. Refresh the LMS title, outcome target, restriction flag, and unlock/due/lock times. The bootstrap launch updates course/user membership without creating an assignment.
3. Commit before issuing the short-lived, one-use login token and redirecting to the selected UI with the assignment key and token. A continuation whose prerequisite is unfinished still gets its assignment row.
4. `Hello(token)` consumes the token and creates a database-backed session, returning the raw session key, authenticated identity, role flags, and client version policy. Subsequent `Hello` calls use an empty token and `authorization: Bearer SESSION_KEY`; they validate the session and need not return a replacement key.
5. Authenticate subsequent protected TA requests from that metadata. Cached client roles, request user IDs, cookies, and possession of an assignment key are not authorization. Problem-type reads are public TA operations; problem-type mutations require admin access.

Tokens are in-memory launch credentials; durable sessions are database-backed. A restart may invalidate an unused launch token without invalidating all durable sessions. Session secrets and daycare signing secrets have distinct responsibilities.


Assignment discovery and workspace reads
----------------------------------------

`ListAssignments` and `GetAssignment` use the same server-owned visibility and download policy. Owners see their assignments; course instructors can inspect assignments in their courses. Restricted student assignments are filtered or denied when the request IP is not allowed. Global cached instructor visibility does not grant access to every course.

Download status distinguishes available, not open, and prerequisite not ready. Future `unlock_at` prevents student workspace downloads. A continuation requires a passing saved final step in the preceding slice for the same student and course. Course instructors bypass download timing and prerequisite restrictions. `lock_at` does not hide an assignment or block downloads, student saves, execution, or progression; it governs student LMS passback. Due dates are presentation data, not a separate execution gate.

1. `GetWorkspace` requires an explicit `CURRENT` or `STEP_START` file state; reject omitted and unknown enum values. Recheck assignment access and download availability even when the client previously listed the assignment.
2. Resolve step zero to the assignment's current in-scope step. Explicit steps must exist in the problem-set scope. Progress selects the first unpassed scoped step, or the final scoped step when all have passed.
3. For `CURRENT`, use the saved commit's file map when a commit exists, including an empty saved map. Otherwise construct step-start files. `STEP_START` always constructs the reset source rather than using the current step's saved work.
4. Construct step-start student files by walking backward through preceding steps and linked continuation slices until a saved commit supplies the base, or step one is reached. Replay starter overlays for every unsaved intervening step and the requested step in chronological order. Step one begins with its starter files; authored solutions are never a fallback. Saved file maps are authoritative, including empty maps and omitted paths. This reconstructs instructor workspaces across unfinished slices without creating commits. Refresh canonical problem-type files over authored regular files and return separate system/student maps, action names, and slice bounds.
5. Return solution files only when explicitly requested and authorized for an author or instructor of the assignment's course. `include_contents=false` retains file names with empty contents; it is not a different ownership model.

Read access to an explicit step is distinct from permission to save it. Every owner save independently requires all earlier in-scope steps to have passing saved commits and rejects an earlier step once later in-scope saved work exists. A passing step requires both `report_card.passed` and score `1.0`.

Assignment scores are weighted averages: step scores within each scoped problem, then problem scores within the set. Missing scores count as zero. Out-of-scope steps cannot affect a slice's score or completion.

Assignment reads resolve availability and metadata through `assignment_policy_fields`, then viewer access through `accessible_assignment_policy`. Permission checks, assignment detail reads, and commit policy consume these unscored views. List presentation adds scores through `assignment_list_fields` or `accessible_assignment_fields`. `assignment_scores` correlates both weighting stages to each selected assignment key; single-assignment reads do not aggregate unrelated assignments. `passed_commit_steps` filters the unique current commit rows directly, allowing progression and prerequisite joins to look up individual step keys.

Existing databases receive these view definitions through `setup/update-assignment-views.py DATABASE`, which reads the canonical schema and transactionally replaces the affected views, validates dependent views, and preserves tables and indexes. `make -C tests assignment-views-check` checks upgrade atomicity, data preservation, and empty-set scoring. For deployment, build the updated server first, stop it with `doas rc-service codegrinder stop`, run the view update against the configured database, then start it with `doas rc-service codegrinder start`. Startup refreshes planner statistics. Database-copy validation does not replace the live database, which continues accepting student work until shutdown.


Workspace persistence
---------------------

1. Authenticate `SaveWorkspaceCommit`, require an assignment and empty action, and load the assignment commit policy and scoped grading context in one write transaction.
2. Enforce restricted access and validate every submitted path against the student whitelist. Ownership comes from the database view, not a rewritten request assignment key.
3. For an owner, enforce step sequencing, upsert the commit metadata, and replace its entire file set. Ignore submitted score, transcript, and report card. On an existing graded commit, a files-only save preserves the previous grading fields; it does not certify the new bytes as freshly graded.
4. Return `SAVED` only after persistence commits. An authorized non-owner inspection returns `NOT_SAVED_NOT_OWNER` without changing student state. The current policy does not return `NOT_SAVED_LOCKED` for owner saves.

This operation neither allocates a daycare bundle nor posts an LMS grade. A whitelist permits paths; it is not a requirement that the request include every permitted path.


Server-coordinated execution
----------------------------

`RunAssignmentAction` accepts authenticated assignment/problem/step identity, action, note, and student files. It constructs its own timestamps and actor identity. Its first write transaction enforces commit-policy views, restricted access, the student-file whitelist, and step sequencing; saves owner files only; and hydrates canonical system files, action command, parser, limits, and problem options. Invalid action/type/path resolution rolls back the files-only save. Non-owner instructor inspection retains the assignment owner and remains non-mutating.

After that transaction commits, the coordinator passes the typed runtime snapshot directly to local daycare. There is no runtime encoding, HMAC, hostname routing, or timestamp-freshness check. `ExecutionUpdate` carries output events and a completed in-process runtime value. The same container engine, lifecycle locks, capacity accounting, replacement policy, output capture, and stable snapshot rules apply to both transports. Only the legacy `Daycare` adapter decodes/verifies input envelopes and encodes/signs final grade envelopes.

For `grade`, completion starts a new write transaction that rechecks current commit access, ownership, whitelist, and step sequencing and persists the server-held result. Only a saved owner grade initiates passback bookkeeping and asynchronous LMS posting after transactions close. The final stream result carries the grade, save status, and the server's lock decision. A non-grade action instead returns an explicit completion with its initial save status and performs no result save or LMS post. A missing completion or stream error is failure. Execution success is distinct from durable grading success.

`RunAuthorProblem` accepts an author draft and either explicit create/update intent or an action with a selected step. A read transaction overlays canonical type files, applies effective-tree ignore rules, derives cumulative student ownership, checks continuity, and retains regular/starter/solution files and runtime snapshots in server memory. Execute validation steps sequentially outside transactions, streaming step-tagged events and reports. A failed grade stops validation without publishing any problem rows. After every grade passes with score `1.0`, one write transaction enforces existence intent and assigned-problem shape and persists exactly the prepared regular/starter files and validated solution files. Create also creates the default same-ID problem set. Action mode runs only the selected step and never persists, including an explicitly selected `grade` action. Problem-set-only saves retain `SaveProblemSet`.

One client/server execution deadline covers preparation, queueing, all execution steps, and final persistence; it defaults to 120 seconds. Disconnect or expiry drops the coordinator's execution stream, causing the daycare worker to cancel supervised work while retaining lifecycle ownership and capacity until cleanup completes. The initial assignment files-only save survives interruption. A final save may commit even when its acknowledgement is lost; do not automatically replay the request. A completed result can be persisted and delivered while container removal finishes, as with legacy grading.


Legacy grade and action submission
---------------------------------

1. `SaveUngradedCommit` requires the authenticated actor to match the outer `GradingCommit.user_id`. Clear caller-provided grading output and perform the same files-only owner save and sequencing checks as workspace persistence. Non-owner inspection stays non-mutating.
2. In that transaction, resolve the canonical action, container, command, parser, limits, problem options, and step context. Combine authored regular files, canonical type files, and submitted student files into a runtime snapshot. Use the configured local hostname after checking support for the requested problem type, unless a host was explicitly supplied through the existing protocol. Failure to resolve the action or host rolls back the pre-execution save.
3. After the transaction, sign the runtime snapshot and return it with the save status. The client sends this exact envelope to its named daycare. TA session credentials are not needed by daycare, and TA/daycare do not contact each other during execution.
4. For a non-grade action, daycare events and normal stream completion are the result. There is no final grade persistence RPC. For `grade`, daycare returns a signed final bundle; the client must submit it to `SaveGradedCommit`.
5. `SaveGradedCommit` verifies the signature and authenticated actor, rechecks current access, ownership, file validation, and sequencing, then persists the signed commit's files, transcript, report card, and score in one transaction. Only a saved owner result can trigger passback. Runtime success alone is not database persistence or an LMS acknowledgement.

An execution failure can produce a signed failing report; a transport or setup failure can prevent a final bundle altogether. Neither erases a successful pre-execution save. Retrying execution is a new request subject to the daycare's single-container policy.


Daycare admission, execution, and cleanup
-----------------------------------------

Execution uses the local daycare. Student submission and author preparation default to the configured public hostname and require local support for every requested problem type. Author preparation checks all draft types together. The existing student submission hostname override remains accepted; daycare admission still requires the signed host to match its configured hostname. Capacity is enforced by the runtime semaphore, not by host discovery or registration.

1. The legacy transport verifies the runtime envelope, host binding, required identity fields, matching commit/action, and timestamp freshness before execution, accepting at most 15 minutes of absolute timestamp drift. The new coordinators supply trusted in-process values directly. Resolve command arguments and effective resource limits once before admission, including checking file-limit conversion for overflow.
2. Mark the new run active for its user-derived container name and immediately signal the preceding worker to stop. Acquire the shared per-user lifecycle lock, then a capacity permit; both waits observe deadline, disconnect, and replacement. The predecessor retains lifecycle ownership through reconciliation. A weak-reference registry preserves the same lock while any worker owns or waits for it, even if a newer queued request disconnects. No registry mutex spans Docker operations.
3. Recover an existing labeled daycare container with the same name by listing its full ID and removing that ID. Verify the image is installed. Use `docker create --pull=never` with networking disabled, capabilities dropped, no new privileges, an unprivileged user, and memory/process/CPU/file/descriptor limits. A random process-instance identifier plus run number labels the creation. After creation returns its ID, recheck cancellation through the request scope, start that ID, and copy a validated tar into the running container's `/home/student/`. Student workspace directories are never host mounts.
4. Execute the signed command within its CPU-derived wall-clock allowance. Concurrent owned futures supervise execution and forward live stdout/stderr into a bounded transcript and client stream. Command exit, execution timeout, and infrastructure failure are distinct internal outcomes. Stop and confirm the container is no longer running before extracting reports or downloads, including when descendants outlive the command. The first successful copy-out is cached for all report reads and downloads. Copy-out accepts regular validated files and does not follow arbitrary guest links onto the host.
5. Fill the report, elapsed command duration, transcript, score, and result timestamp. Deliver an in-process completed runtime before final container removal. The legacy adapter signs and forwards it only for `grade`; the new coordinators handle persistence and completion. Remove the container by ID and release capacity and lifecycle ownership only after successful removal or confirmed absence. Clear active-run bookkeeping only for the matching run. A newer request does not invalidate a delivered result.

Output events are not a bidirectional terminal protocol. Downloaded artifacts are events, not automatic replacements for the signed commit's submitted files. Browser CORS support belongs at this execution boundary. Container image availability, matching secrets/hostnames, sufficient disk space, and a functioning container command are deployment dependencies.


Daycare goals and cancellation boundaries
-----------------------------------------

The primary operational goal is to keep a small shared server responsive when a whole class submits at once. An early browser interface appeared unresponsive during grading, so students repeatedly clicked Submit and accumulated execution work. Cancellation, replacement, capacity admission, and visible action progress are resource-management requirements grounded in that failure mode. They are not mechanisms for exactly-once grading or preventing students from grading repeatedly.

The two concurrency rules solve different problems. `capacity` bounds the total number of execution containers across users through one shared semaphore. The user-derived Docker name and per-user lifecycle lock prevent overlapping containers and conflicting Docker mutations for one user. A new request signals its predecessor before waiting for ownership or capacity so the old worker can stop, clean up, and release its slot. A disconnected or superseded queued request must leave the queue without ever acquiring capacity. Do not replace user-derived names with unique session names to avoid contention.

Each accepted run has a process-local run ID, a replacement signal, an absolute request deadline, and an output channel whose receiver belongs to the RPC response body. Deadline expiry, detected client disconnect, or a newer run interrupts queueing, startup, upload, execution, output delivery, and result extraction. The response stream independently enforces the absolute deadline and drops its receiver when reporting deadline exceeded, even if its worker is reconciling Docker. Losing the response body closes the receiver; helpers must not wait for a later stdout event to detect that closure. Actual network failure is actionable when the transport detects it, which may lag the client's observation; replacement covers that interval.

The worker owns its subprocess and pipe futures; no detached stdout/stderr reader or blocked stdin writer retains request state. Execution and forwarding are polled concurrently, so a connected non-reading client cannot suspend the execution deadline. That deadline covers pipe writes, process completion, pipe reads, and backpressure. Killing a Docker exec CLI does not terminate the student process: container stop and removal remain mandatory. An execution timeout stops the container before trying to deliver the signed failing report; subprocess transport and startup errors remain infrastructure failures rather than signed student failures. Report retrieval retains its separate convention: unavailable report data is logged and parsed as an invalid report, producing a failing grade.

Container creation is deliberately not abandoned when its request expires or is superseded. The owner continues observing the create CLI, holding its user lock and capacity permit; expiration records `daycare_creation_quarantined`. A failed CLI or missing ID is an unresolved creation, since the daemon may still complete it. Recovery lists containers by the unique creation label until it finds and removes the resulting ID. An empty listing alone cannot prove that a failed creation will not finish later. Image availability and effective limits are checked before creation to avoid quarantining ordinary configuration errors where possible.

Cleanup deliberately outlives the cancelled request and does not use its expired deadline or output channel. Stop receives a two-second budget and forced removal receives a separate fresh five-second budget. Subprocess timeout handling allows up to one additional second to kill/reap its CLI child. Failed removals are checked against a successful full-ID listing to distinguish absence from engine failure. A removal or recovery failure retains capacity and lifecycle ownership and retries with delays of one, two, four, and up to thirty seconds, recording quarantine events. This deliberately sacrifices availability when Docker state cannot be established. A failed creation that never produces an identifiable container can remain quarantined until operator intervention; restarting the server loses process-local ownership and is not proof that a daemon operation has ended. There is no destructor-based guarantee after a panic or server exit.

A successful signed grade bundle is intentionally delivered after stopping the container and extracting a stable workspace, but before final removal. Once delivered, the client can drop its stream and immediately call `SaveGradedCommit` while removal continues. Do not move removal ahead of that result merely to align RPC completion with container absence. Do not reject a reliable completed grade merely because a newer run exists. Duplicate completed grade saves or Canvas notifications are acceptable; result invalidation, durable run IDs, and exactly-once passback are not goals. The initial files-only save remains durable whether execution finishes, fails, disconnects, times out, or is replaced.


Daycare time budgets and resource overrides
------------------------------------------

Every client RPC has a timeout. Native `grind` defaults to ten seconds for ordinary RPCs and connection establishment, and 120 seconds for daycare. `--timeout SECONDS` overrides ordinary RPC timeouts; `--daycare-timeout SECONDS` overrides the daycare timeout. The latter is independent of ordinary bookkeeping calls. Exam browser transports use the same ten-second and 120-second defaults; the exam page aborts its active daycare fetch when leaving the page or starting a replacement daycare call. The minimally maintained web interface has transport deadlines but otherwise retains its existing presentation.

Daycare reads the standard `grpc-timeout` metadata and propagates the resulting absolute deadline into the worker. A caller omitting it receives the server's 120-second fallback. The entire request, including queueing and preparation, is subject to that request deadline. Fixed daycare defaults avoid requiring an extra metadata RPC or changing submission messages, and remain usable when a future combined RPC begins before a signed runtime exists. The signed runtime is not decoded by clients to derive the request budget.

Student resource limits are a separate policy. Start from the problem-type action's limits and apply signed per-problem options `maxCPU`, `maxFD`, `maxFileSize`, `maxMemory`, and `maxThreads` in order. These options require exact keys and integer values, without whitespace normalization; reject malformed recognized values and nonpositive effective limits. Unknown options remain available for unrelated conventions such as downloads. `maxSession` and `maxTimeout` are obsolete interactive-session concepts, not supported execution limits.

Apply effective memory/swap, process, file-size, descriptor, and CPU limits to the container. `maxCPU` supplies the operating-system CPU limit; it is not an aggregate cgroup CPU-time counter. Student command execution separately receives a wall-clock allowance of `2 * maxCPU + 5` seconds, bounded by the remaining request time. Preparation, upload, report extraction, and cleanup do not consume that CPU-derived allowance. The container's sleep process uses the remaining overall request time plus a small cleanup allowance, rather than starting a CPU-derived clock during setup. Authors needing a run longer than the default request budget must also arrange a longer client daycare timeout.


Daycare output, reports, and artifact snapshots
-----------------------------------------------

Actions exist to show what student code does. Forward stdout and stderr in chunks while the command runs, with bounded channel backpressure. Retention limits must not suppress subsequent live output: an infinite output loop should remain visible until interrupted or timed out. The command helper can bound its retained diagnostic buffers independently. Capture event order as chunks arrive; do not collect complete stdout and then complete stderr before constructing the transcript. Bytes produced before a command timeout remain in the transcript available for a failing grade.

The saved transcript retains at most 100,000 stream-data bytes and 500 events; adjacent stream events of the same kind may merge. Continue draining and transmitting output after the saved transcript fills. Truncation counters belong in operational logs. These limits protect database storage, not the number of bytes a live client is permitted to receive. Artifact events are separate byte maps and follow the workspace-copy limits and regular-file/path validation. An execution timeout also emits an error event, so actions display the reason for stopping and failing grades retain the diagnostic alongside preceding output. Infrastructure failures use the stream's terminal error response.

Both CLI and exam grading consumers suppress live output, wait for the grade verdict after the coordinated result save, and replay the saved transcript only on failure. Successful grading should stay quiet apart from its verdict/progression messages. Non-grade actions display live output, require an explicit completion result, and perform no final grade save. The retiring `www/web` interface still uses the signed legacy flow and displays grading output directly; keeping its presentation fully aligned is not a priority.

After command completion, stop the container and confirm `State.Running` is false before report or download extraction. The first read copies `/home/student/.` from the stopped container and validates the tar into an immutable path-to-bytes map. Later reads reuse that map, including an empty successful snapshot; a failed copy is not cached as an empty success. Workspace extraction permits at most 100,000,000 content bytes, 20,000 archive entries, and 4,096 bytes per regular-file path. XML reports are limited to 5,000,000 bytes before parsing. These limits bound host-side processing and do not provide an aggregate container disk quota. Do not automatically replace submitted commit files with copied-out artifacts.

Download patterns are parsed once per selection into byte-oriented literals, stars, single-byte wildcards, and character classes. Matching uses two dynamic-programming rows without recursive backtracking. Preserve stars crossing directory boundaries, byte rather than Unicode-character matching, negated/ranged classes, and literal unmatched opening brackets. Exact paths use direct map lookup.

For xUnit, a testcase passes only when its status is absent, empty, or `run`, and it has no failure, error, skipped, or disabled child. In particular `status="notrun"` is failing. Preserve failing command exit status even if the XML reports passing tests. Check XML interprets `success` as passed and every other result as failed. Empty or malformed reports fail. Summaries include elapsed student-command time, and the signed report carries that duration explicitly. A passing signed grade requires both `report_card.passed` and score `1.0`.


Go comparison and regression audit record
-----------------------------------------

The comparison baseline is Git commit `1c100ae5ced464ec7a603b28a8db28d36281041f`, the parent of `b12eeb6` (Go deletion on February 21, 2026). The last daycare change is `8afabe0` on February 9, 2026, which added `cmd.WaitDelay = time.Second` to Docker copy and execution commands. Relevant source paths at that commit are `server/daycare.go`, `server/rpc.go`, `server/xunit.go`, `cli/helpers.go`, and `cli/grade.go`.

| Behavior                    | Final Go implementation                                         | Current contract                                                        |
|-----------------------------|-----------------------------------------------------------------|-------------------------------------------------------------------------|
| Request cancellation        | Passed `stream.Context()` through the worker to Docker commands. | Deadline, stream loss, and replacement interrupt daycare work.          |
| Queue cancellation          | Capacity-channel send did not select on context cancellation.    | Abandoned queued requests exit without waiting for a slot.               |
| Client daycare deadline     | CLI used `context.Background()` without a daycare deadline.      | Fixed timeout with native CLI override; no metadata round trip required. |
| Pipe completion             | Copy/exec used one-second `WaitDelay`.                           | All pipe work is owned and bounded by the command future and deadline.  |
| Same-user replacement       | Removed a conflicting name after acquiring capacity.            | Signal the old worker and preempt before capacity admission.             |
| Live output                 | `eventWriter` forwarded writes and captured transcript data.    | Chunked live events remain independent of transcript retention.          |
| Grade presentation          | CLI ignored live events and replayed transcript on failure.     | Preserve that behavior in CLI and exam.                                 |
| Grade delivery and cleanup  | Sent signed result before deferred shutdown.                    | Preserve early delivery and independent cleanup.                        |
| Artifact copy-out           | Cached the first copied workspace in the nanny.                 | Cache the first successful validated workspace map per container.       |
| xUnit status                | Checked testcase status as well as failure children.            | `notrun` and other non-run statuses cannot pass.                         |
| Elapsed summary             | Included time since nanny startup in report summary text.       | Include student-command duration in summary and report duration field.  |
| Override whitespace         | Trimmed keys/values and skipped malformed options.              | Keep exact Rust parsing and reject malformed recognized values.        |

The Rust port previously detached the execution worker from transport cancellation, buffered stdout/stderr until command exit, lost captured output on timeout, omitted testcase status and elapsed summaries, recopied the workspace for each extraction, and calculated native daycare timeouts from defaults while ignoring overrides. These are the regression paths the current invariants and tests are intended to protect. Go is evidence for intended behavior, not an instruction to restore its uncancellable capacity wait or missing client deadline.

`DaycareRequest.args` had no effect in the final Go implementation: the RPC passed it into `NewNanny`, whose body ignored it, and the CLI sent an empty list. Before `d1aa297` on May 8, 2024, interactive sessions used arguments to supply `COLUMNS`, `LINES`, and `TERM` environment values. Interactive TTY support was removed because it did not work reliably for the target clients. The protocol now reserves the removed field number and name. Do not restore terminal input, idle-session limits, or arbitrary command arguments as part of output streaming.

Behavior tests cover live output before command completion; disconnect while queued and executing; absolute stream deadlines; same-user replacement across delayed creation; late daemon creation after CLI failure; a disconnected pending replacement preserving lifecycle ownership; backpressure-independent timeout and stopping; cleanup failures retaining capacity after grade delivery; independent stop/removal budgets; refusal to extract an unconfirmed live workspace; bounded glob matching and archive inputs; and the existing report, transcript, signature, limit, and cache invariants. Fake-engine tests coordinate CLI completion independently of daemon-visible state. They do not prove Docker or HTTP transport behavior. Run the real-container regression with `make -C server test-only TEST_ARGS='daycare::tests::docker_background_writer_is_stopped_before_snapshot_and_container_is_removed -- --ignored'`; it requires Docker and the installed `codegrinder/python:latest` image, overridable with `CODEGRINDER_TEST_IMAGE`. It creates a uniquely named test-user container, leaves a detached writer running after command exit, checks that copy-out occurs while stopped, and verifies final removal.


LMS passback and recovery
-------------------------

After graded persistence commits, a separate short transaction determines passback work and records its state. A locked assignment records the lock reason; a missing outcome target records the no-target reason. Otherwise record pending, calculate the assignment score, and prepare the report before scheduling network work.

The background task signs the LMS request and retries transient failures up to ten attempts, starting at ten seconds and doubling to a five-minute cap. Permanent failures stop immediately and are recorded separately from exhausted transient failures. Success records posted in a new transaction. Startup recovery selects pending and transient-failed assignments, waits a randomized delay, and rechecks status and target availability before preparing another attempt. Permanent failures are not automatically retried at startup. Current recovery and already-scheduled retries do not recheck lock dates before each HTTP attempt; the lock decision belongs to the original submission path, not a guarantee that delivery occurs before the deadline.

The grade RPC can succeed before the LMS responds. A failure after commit cannot roll back the saved student grade. Passback state is assignment-level bookkeeping, not a guarantee of exactly-once external delivery. Relaunching from Canvas refreshes an extension; rerunning grade can then initiate passback under the updated dates.

Canvas instructor launches do not supply an LMS passback target. Instructor lock-date handling therefore does not need a separate grade-posting exception. This does not change the course-instructor exemption from student download restrictions.


Legacy author preparation, validation, and save
----------------------------------------------

1. Authenticate author access and accept an ordered `AuthorProblemDraft` of metadata, authored files, and `_starter/` files. `PrepareProblem` persists nothing.
2. Overlay canonical problem-type files, process hierarchical Git-style ignore rules on the effective tree, and exclude canonical collisions from authored persistence. Derive cumulative student paths from starter paths introduced so far. Every cumulative path must have an authored solution at every subsequent step. Preserve supplied bytes.
3. Build and sign a validation runtime for each step using the same runtime/commit shape as student grading. The client runs every grade validation through daycare and attaches its signed results before `SaveProblem`.
4. In one save transaction, enforce explicit create/update intent and verify exactly one step, solution commit, and signed passing validation per step. Reject missing, extra, mismatched, tampered, unsigned, or failed results before any problem rows are written. Persist solution bytes matching the prepared solution, regular bytes matching the validated runtime, and starters matching the signed bundle.
5. Create mode also creates the same-ID, one-problem default problem set with weight one and no slice. Assigned problems may change metadata and files but not step count or per-step problem type. An interactive preparation action never authorizes persistence by itself.

`SaveProblemSet` saves metadata and memberships/weights with explicit create/update intent; it does not execute validation. Enforce unary slices, adjacent continuation bounds, and existing problem references. Once assigned, membership, slice bounds, and continuation shape are immutable; metadata and weights remain editable.

Admin problem-type saves transactionally upsert retained metadata/actions/files and delete only omitted entries in the submitted complete replacement set. Do not delete/recreate the parent row. Canonical-file changes affect future workspace refreshes and runtime preparations; they are not student uploads.


Operational logging
-------------------

Operational records use stderr. Lifecycle records carry severity, a stable event name, and named fields on one line; the system logger supplies the timestamp and service prefix. Daycare identity is attached only after signature validation; host, actor user, assignment owner/course/problem set, problem, step, action, and a process-local run number identify each accepted run. The run number is not a protocol field or a durable identifier across restarts. Logs never intentionally include session keys, signed envelopes, workspace contents, or routine student stdout/stderr.

An accepted daycare run logs a completion summary with total duration (including queueing and cleanup), grading outcome, and any execution error. Ordinary command exits also produce one resource report combining container state and cgroup usage; routine admission, staging, command exit, and successful cleanup produce no separate records. Replacement of an active same-user run records both run numbers. Container creation, workspace upload, command execution, report retrieval, artifact download, stream closure, and cleanup failures retain their causes. A failed student report is an ordinary execution outcome, not by itself an infrastructure error. Output/transcript truncation records discarded counts while preserving existing capture limits.

After ordinary command exit and before stopping, bounded Docker inspection records container state, container exit code, and OOM status separately from the student command exit code. Cgroup v2 sampling reads CPU counters in microseconds, peak memory in bytes, peak process count, and memory event counters. Urgent cancellation and execution timeout stop work without waiting for these diagnostics. Unavailable counters and inspection failures are explicit and cannot prevent cleanup. Removal errors distinguish confirmed absence from failure to establish absence; unresolved failures produce quarantine records and retain capacity. Diagnostic collection does not change the one-container-per-user policy or introduce workspace mounts.

Unsupported local execution requests log the requested problem types. Workspace saves, including pre-daycare and graded persistence, produce no routine records. LMS passbacks log one final success or failure after retries, with attempt count; scheduling, intermediate retry failures, and locked/no-target/pending bookkeeping produce no routine records. Unexpected passback preparation or status-persistence failures remain explicit. Unexpected gRPC errors are logged at status conversion, with operation/actor context for grade submission and persistence. Database transactions taking at least 500 milliseconds log the operation closure name, time acquiring the initial transaction lock, and subsequent transaction time; failed begin and rollback operations are explicit. Deferred read transactions can acquire later locks during SQL execution, so the initial lock duration does not measure all possible SQLite waiting.


Audit boundaries and dependencies
---------------------------------

Preserve end-to-end checks at these boundaries: unauthorized or restricted access; missing/unknown file state and invalid paths; continuation download and step sequencing; files-only saves retaining grading fields; signed validation tampering; non-owner execution without persistence; post-lock student progress without passback; overlapping same-user runs with cleanup; and passback failure/restart recovery.

The implementation trace begins in [service.rs](service.rs), [lti.rs](lti.rs), [store.rs](store.rs), [mutations.rs](mutations.rs), [daycare.rs](daycare.rs), and [passback.rs](passback.rs). SQLite schema/views, protobuf generation, the shared Rust workspace, Caddy, installed problem types/images, and configured LMS/signing secrets are operational dependencies.

Use `make -C server check` for formatting and Clippy, then `make -C server test TEST_ARGS=...` for affected behavior. All Cargo checks/builds/tests use the release cache. Cleanup must preserve persistent data; `mostlyclean` also preserves deployed executables/assets.


Attended Respondus quiz entry
----------------------------

The VM interface under `/vm/` is independent of admission. Existing `/lti/problem_sets/exam/SET` launches retain ordinary authenticated sessions plus testing-center IP policy. `/lti/problem_sets/quiz/SET` uses attended redemption instead. `assignments.restricted` continues to represent IP restrictions; membership in `quiz_assignments` adds the separate quiz-session requirement. No protobuf fields or RPCs change.

1. Canvas launches `/lti/picker` using signed LTI 1.1 `ContentItemSelectionRequest`. A signed Instructor/TA role authorizes selection in the supplied `context_id`. The picker lists problem sets and offers CLI, web, testing-center VM, and Respondus quiz modes. Existing manually pasted launch URLs remain supported. A thirty-minute signed picker ticket carries course, consumer key, opaque Canvas data, and the authenticated HTTPS return URL; subsequent form submissions cannot replace them.
2. Quiz configuration accepts the matching Canvas/Respondus password transiently. It generates two HMAC-SHA256 tags with the server session secret, distinct assignment/connector purpose labels, and JSON-encoded version/course/problem-set/password inputs. Neither password nor an unkeyed password verifier is persisted. Tags use 43-character unpadded URL-safe Base64. Links are `/lti/problem_sets/quiz/SET?tag=TAG` and `/quiz/connect?tag=TAG`; course and set are not repeated as query fields. The assignment URL is returned through a signed LTI content-item response. The instructor copies the separately tagged connector URL into the Canvas quiz and configures it to open a new tab, require Respondus and the matching password, and allow this CodeGrinder domain. A password or course change requires replacing both links.
3. A quiz assignment launch verifies Canvas OAuth including URL query parameters and obtains the course from signed `context_id` and the problem set from the request path. It accepts both standard query/body signing and Canvas’s default behavior of copying query values into POST fields and signing each copied value once; conflicting query/body values are rejected. Signature-failure responses expose neither submitted nor computed signatures. It requires a configured allowed station IP and a local reverse proxy peer. In one write transaction it performs the usual assignment/user/course/passback upsert, records quiz assignment-tag membership, and replaces that station's pending entry. The pending row stores the assignment key, assignment tag, station IP, random zero-padded six-digit code, and creation/expiry times. It grants no ordinary login token and exposes no workspace. The displayed identity and code instruct the student and attendant to write down the code and switch to Respondus.
4. The quiz connector GET requires an allowed station and asks the attendant to verify Respondus, enter the code, and re-enter the password. Its POST checks the same exact normalized IP, pending-entry lifetime of ten minutes, code, both HMACs using the pending entry’s course/problem-set identity, and authoritative assignment download availability. Five attempts exhaust an entry. A persistent station budget allows twenty submissions in ten minutes and survives repeated assignment launches. Validation failures commit attempt counts; database failures roll back. Expired station-budget records are removed during redemption.
5. Successful redemption atomically consumes the pending entry, revokes earlier quiz sessions at that station or for that assignment, and creates a normal hashed bearer-session record plus a `quiz_sessions` scope record. A new preparation alone leaves a same-password active session usable. Ten-minute expiry applies to pending entry, not the active exam. Session expiry uses existing configured session expiry policy.
6. A no-store HTTP redirect opens `/vm/` with the bearer key and identity in the URL fragment. The browser removes the fragment immediately, stores the key in tab-scoped session storage, and displays the student/course/assignment identity as text in a modal dialog. Only its Continue button dismisses the dialog. The client then authenticates through existing `Hello` and loads normal assignment workspaces. Reload uses tab storage; losing that storage requires attended entry again. The fragment is never sent in an HTTP request. This is practical tab-session binding, not browser attestation.
7. Session authentication retains quiz scope and verifies its station address. Quiz scopes clear cached global role flags. Assignment reads, list filtering, workspace access, files-only/legacy/graded saves, and coordinated execution authorization check the scope against current assignment tag and live database session expiry/revocation. A scope can authorize only its own assignment; ordinary student sessions cannot access quiz-gated assignments even at approved IPs. Course instructors retain inspection access. Final grade persistence rechecks live scope after execution, and normal passback uses the original LTI assignment target. Session scope records survive removal of quiz membership so a former quiz key can never turn into an ordinary login.

A signed non-quiz LTI launch restores that assignment's ordinary or testing-center workflow atomically with its launch upsert. Assignment identity remains user/course/problem-set: separate Canvas links for the same set in one course share the record and can switch its admission policy. Do not publish simultaneous fallback and quiz links for the same course/set when quiz enforcement is required; use a distinct problem set for separately available fallback work.

Quiz launch, connector GET, and connector POST capture every header value, including repeated/non-UTF8 values encoded as base64, into `quiz-headers.jsonl` beside the configured database. `CODEGRINDER_QUIZ_LOG` overrides the path. Records include UTC time, stage, socket peer, and extracted station address. New files use mode 0600. These protected research logs can contain header credentials; rotate and retain them deliberately outside ordinary operational logs. Bodies and entered passwords are excluded. Failure to write the diagnostic record fails the entry request and is logged centrally without returning filesystem details. The updated Caddy template overwrites `X-Real-IP` from its direct peer; Caddy manages `X-Forwarded-For` using its standard proxy behavior. A deployment with another upstream proxy must establish authoritative station forwarding before enabling quiz entry.

Deployment and environment validation:

1. Back up the existing database and apply `setup/migrations/quiz.sql` followed by `setup/migrations/quiz-tags.sql` once (installations that already applied `quiz.sql` need only `quiz-tags.sql`) with the server stopped. Fresh databases use `setup/schema.sql`. The server does not auto-migrate existing databases.
2. Deploy the built server and VM client assets using the component build workflows. Update the Caddy dynamic-route matcher for `/quiz/*` and authoritative IP headers. Ensure the service can append its dedicated quiz log.
3. Refresh the Canvas tool configuration from `/lti/config.xml` to enable the assignment picker. Manual launch URLs continue to work. Configure both quiz links with the picker and use a distinct set if retaining a separately published fallback.
4. On a real testing-center station, verify that regular Chrome and Respondus reach the server with the same unique station IP. Validate picker return, attendant identity/code displays, Respondus password and domain settings, VM boot/terminal/editing, reload, save, grade/passback, session replacement, and browser closure. Check IPv4/IPv6 consistency and headers from both browser paths. Headers and connector-link possession are evidence, not proof of Respondus execution; the attendant's password entry and observation establish that step in v1.
